Self-Hosted Runners
===================

This repo now separates PR CI from slow platform matrix jobs:

- PR fast lane:
  - dashboard
  - typos
  - check
- Slow platform matrix:
  - check-arm
  - check-riscv
  - check-windows
  - release artifact builds
  - these run on push, schedule, or workflow_dispatch

There is also a manual workflow:

- .github/workflows/ci-self-hosted.yml

It is meant for repo-owned machines such as Mini 3, ARM boxes, or Windows builders.

Runner Labels
-------------

Use these labels exactly so the workflow can target the right machines:

- Fast Linux x64 runner:
  - self-hosted,linux,x64,octos-fast
- Linux ARM64 runner:
  - self-hosted,linux,arm64,octos-arm
- Windows x64 runner:
  - self-hosted,windows,x64,octos-windows

Prerequisites
-------------

1. Install gh and authenticate with a token that can create runner registration tokens.
2. Install build dependencies on the runner host:
   - Rust toolchain
   - git
   - curl
   - platform-native compiler toolchain
3. For Linux/macOS, use:
   - scripts/setup-github-runner.sh

Fast Linux Runner Example
-------------------------

    cd ~/home/crew-rs-port

    scripts/setup-github-runner.sh \
      --name mini3-octos-fast \
      --labels self-hosted,linux,x64,octos-fast

Then launch it:

    cd ~/.github-runners/mini3-octos-fast && ./run.sh

If you want it as a Linux service:

    cd ~/home/crew-rs-port

    scripts/setup-github-runner.sh \
      --name mini3-octos-fast \
      --labels self-hosted,linux,x64,octos-fast \
      --service

ARM64 Runner Example
--------------------

    cd ~/home/crew-rs-port

    scripts/setup-github-runner.sh \
      --name arm-builder \
      --labels self-hosted,linux,arm64,octos-arm \
      --service

Windows Runner Example
----------------------

Use a standard GitHub Actions runner installation on the Windows machine and register it with:

- name:
  - windows-builder
- labels:
  - self-hosted,windows,x64,octos-windows

Typical manual flow in PowerShell:

    $repo = "octos-org/octos"
    $url = "https://github.com/$repo"
    $token = gh api -X POST "repos/$repo/actions/runners/registration-token" --jq .token

    mkdir C:\actions-runner
    cd C:\actions-runner
    curl.exe -L -o actions-runner-win-x64-2.328.0.zip https://github.com/actions/runner/releases/download/v2.328.0/actions-runner-win-x64-2.328.0.zip
    tar -xf .\actions-runner-win-x64-2.328.0.zip
    .\config.cmd --unattended --url $url --token $token --name windows-builder --labels self-hosted,windows,x64,octos-windows --replace
    .\run.cmd

Triggering The Workflow
-----------------------

From GitHub Actions UI:

- workflow: CI (self-hosted)
- inputs:
  - ref
  - include_arm
  - include_windows

From CLI:

    gh workflow run "CI (self-hosted)" \
      --repo octos-org/octos \
      -f ref=main \
      -f include_arm=true \
      -f include_windows=false

Recommended Rollout
-------------------

1. Register one Linux x64 runner first with octos-fast.
2. Confirm CI (self-hosted) succeeds on the fast lane.
3. Add ARM64 runner with octos-arm.
4. Add Windows runner with octos-windows.
5. Only after that, decide whether any self-hosted jobs should become required checks.

macOS Runner Pool (octos-mac)
-----------------------------

Repo-owned Apple Silicon machines form one pool. Every member carries the
same labels, so GitHub hands each job (and each matrix shard) to whichever
member is idle; adding a machine adds capacity without workflow changes.

- labels:
  - self-hosted,macOS,ARM64,octos-mac
- switch:
  - repository variable OCTOS_MAC_POOL=on routes the jobs below to the pool;
    any other value (or unset) sends them back to hosted macos-15 at once
- jobs that use the pool, and only for trusted events (push to main,
  merge_group, workflow_dispatch, schedule):
  - ci.yml: check-darwin, build-macos-arm, e2e-tool-regression, security
  - nightly.yml: tool-regression-e2e, darwin-tests (3 nextest shards)
- pull_request events, including forks, never target the pool: the repo is
  public and the runners are persistent machines

Shared compiler cache: pool members use sccache with an S3-compatible bucket
on the LAN, so a crate compiled by one member is a cache hit on the others.
Self-hosted jobs skip Swatinem/rust-cache; they keep target/ between runs.
The reference setup is MinIO on one member:

    brew install minio minio-mc sccache cmake
    minio server --address :9000 --console-address 127.0.0.1:9001 ~/ci-cache/minio-data
    mc alias set octosci http://127.0.0.1:9000 "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD"
    mc mb -p octosci/octos-sccache

Register a member (credentials come from the environment, never the repo):

    SCCACHE_S3_ACCESS_KEY=... SCCACHE_S3_SECRET_KEY=... \
    scripts/setup-macos-ci-runner.sh \
      --name macmini1-octos \
      --proxy http://192.168.3.2:7893 \
      --sccache-endpoint http://192.168.3.200:9000

--proxy is only needed where github.com is not directly reachable; it is
written into the runner's .env and does not change system network settings.
Members on different networks: a LAN MinIO only serves its own site. Either
point every member at one hosted S3-compatible bucket (for example Cloudflare
R2: --sccache-endpoint https://<account>.r2.cloudflarestorage.com), or give
each site its own MinIO and accept per-site cache hits. Omitting
--sccache-endpoint falls back to a local cache on that machine.

A machine may host several members (one per runner directory) when it has
the memory for concurrent release builds.
