# Make Octos goals survive disconnects, restarts, and delayed results

**Status** Proposed · **Date** 2026-11-21  
**First client** OctosCode · **First workflow integration** editable PPTX production

## Decision

Give `octos serve` ownership of an unattended goal from admission through delivery. Once the server acknowledges an unattended goal, it must be able to answer three questions after a restart. What work has been accepted? What can run next? If nothing can run, which event or decision will unblock it? OctosCode can disconnect and later obtain those answers through the Octos UI Protocol (OUP). A waiting goal consumes zero model tokens.

Extend the Rust continuation scheduler, supervisor store, and OctoScript workflow host to provide this contract. OctoScript declares dependencies and joins. Domain tools validate work and issue receipts. The host owns durable transitions, timers, and dispatch. The agent still owns planning, editing, and qualitative review. A goal has a completion condition. The first milestone ends when the server can recover an accepted goal and deliver its result without a client or external supervisor. A standing instruction such as “watch this folder for a month” can create new goals even after earlier ones finish. That is a separate product decision with its own acceptance case below.

## Why change the current behavior?

- **OctosCode can show an active goal while no turn is eligible.** The Rust client submits the objective to the server. The ordinary continuation policy checks token and turn budgets, a minimum interval, and an hourly cap. In the examined release it derives the turn cap as `ceil(token_budget / 2500)`. The goal indicator mainly shows status and token consumption. Someone with tokens left cannot tell from that indicator when work will resume. [Client submission](https://github.com/octos-org/octoscode/blob/3b4efa77682cf130a195f6bc6c9a894ab9fd0200/src/store.rs#L2367-L2394) · [Continuation policy](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/autonomy/agent_orchestrator.rs#L15681-L15732) · [Goal indicator](https://github.com/octos-org/octoscode/blob/3b4efa77682cf130a195f6bc6c9a894ab9fd0200/src/app.rs#L3687-L3705)
- **The runtime can confuse activity with progress.** The turn-end check treats a positive token count as progress even if the model reread the same file and produced the same diagnosis. Three consecutive zero-token failures can park a goal. Separately, the completion verifier historically rejected finished peer work when its evidence was missing from the request. The existing fix passes ledger findings to that verifier. [Turn-end check](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/autonomy/agent_orchestrator.rs#L3629-L3666) · [Failure threshold](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/autonomy/agent_orchestrator/contract.rs#L84-L91) · [Verifier evidence fix](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/goal_tool.rs#L1177-L1207)
- **The PPTX work supplies a reusable precedent.** The experimental workflow branch binds each activity to an operation, generation, and validated receipt. A worker can exit before its receipt arrives. Replaying the exit chooses the same successor. The local prototype implements this in `1283ecae0` and tests recovery with periodic draining disabled in `9d3bd3128`. Both commits are unpublished. The upstream integration points are the [continuation scheduler](https://github.com/octos-org/octos/blob/6cde67b0c380b80e2028f8390573a1a636b220b3/crates/octos-cli/src/autonomy/master_continuation_scheduler.rs) and [supervisor store](https://github.com/octos-org/octos/blob/6cde67b0c380b80e2028f8390573a1a636b220b3/crates/octos-cli/src/autonomy/supervisor_store.rs). The [rollout and acceptance tests](#rollout-and-acceptance) specify how to verify the proposed recovery guarantee upstream.

## Execution and recovery contract

1. **Accept an event durably before acknowledging it.** User input, completed tools, worker returns, reviewer decisions, approvals, and due timers enter through one logical intake contract. Identify an event by source and stable occurrence ID. Persist its goal, operation, generation, and payload reference. Waking an in-memory worker is a latency optimization. An event acknowledged just before a process crash remains eligible for dispatch.
2. **Give each independent operation one current owner.** A worker claims an operation with an expiring lease and a monotonically increasing claim number. Completion must match both that claim and the input generation. An expired lease permits recovery. A late worker cannot overwrite newer work. Separate page or task IDs can have live claims concurrently under the configured resource limits.
3. **Commit the result and its next step together.** Accepting a receipt, consuming the input event, and recording the successor or wait must be one durable transition. Use a transaction where the store supports it, or append one authoritative journal record from which pending dispatch can be rebuilt. If the input and effect stores differ, record a pending effect locally and deliver it with a stable idempotency key. Reconstruct ready operations, due timers, and expired leases on startup. Periodic reconciliation can also repair missed notifications.
4. **Record waits explicitly and release the worker.** A wait names its cause, expected event, and optional retry time. An approval may arrive hours later. Persist the deferred call's identity, argument digest and authorization scope, then revalidate the approval against the current generation and permissions before execution. A revoked grant or superseded goal invalidates the old call. Preserve the original profile and workspace boundaries and resolve credentials through the host at execution time.
5. **Make delivery independently recoverable.** Commit a pending notification with the terminal result, its destination, and a delivery key. A dispatcher handles retries. A failed attachment upload leaves the completed artifact intact. If an external destination can neither deduplicate nor confirm a prior send, expose delivery as *unconfirmed* and reconcile before repeating an irreversible action. This design assumes at-least-once event delivery. It requires idempotency or a queryable result at each effect boundary.

Goal state, worker state, and delivery state are separate. A goal can be active while a test runs, complete while its attachment awaits retry, or paused while a stale worker returns. Publish a versioned OUP projection with goal phase, last accepted evidence, pending operation, wait reason, next eligible time when known, budget consumed and remaining, and delivery status. A private stdio backend can advertise foreground execution. Advertise unattended execution only when an independently hosted server has accepted responsibility for recovery. [OctosCode transport and lifetime](https://github.com/octos-org/octoscode/blob/3b4efa77682cf130a195f6bc6c9a894ab9fd0200/README.md#L202-L225)

### Workflow versions during recovery

At admission, persist immutable references to the OctoScript workflow, skills, executor build and review rubric used by the goal. Retain those versions while the goal is recoverable. On restart, use that snapshot. If a version is unavailable, expose the missing dependency. Resolve credentials and check current permissions when work executes. LoopForge uses the saved workflow graph when resuming a run after template edits. Octos should also record which versions a review relied on, since skills can change through JIT updates. [LoopForge workflow lookup](https://github.com/Tencent/LoopForge/blob/a458320ec989c9dbc08a3c4987a63498ff2c87d2/internal/engine/workflow_graph.go#L41-L50)

On an explicit upgrade, record the old and new versions and which acceptance criteria or inputs changed. A change to notification retries preserves page signoffs. A new editability criterion reopens the affected reviews against the existing candidates. A maker runs again only if a finding requires changes to its artifact.

## Progress, completion, and diminishing returns

Keep the objective, acceptance criteria, outstanding work, and evidence references with the goal. Store large artifacts in their existing stores by immutable reference and digest. On recovery load the current operation, relevant evidence, and the user's applicable instructions. Token counts, elapsed time, and tool call counts remain useful for cost and performance accounting.

| Observation | Runtime decision |
|---|---|
| A coding task produces a patch and a failing test now passes | Attach the test command, exit status, and tested tree digest. Advance criteria satisfied by this evidence. Other criteria stay open. |
| A provider times out before returning a result | Record a retryable provider failure, release the worker, and schedule bounded backoff. Surface the reason, retry time, and exhausted retry budget. |
| An agent repeats a repair against the same input and the same material findings remain | Compare persistent finding IDs and fresh evidence. Batch independent fixes into one attempt. After the operation's bounded retry policy is exhausted, record unresolved findings and the best reviewed candidate. A required criterion stays unresolved until met or explicitly waived by its owner. |
| An operation requires judgment or has no mechanical acceptance test | A designated reviewer records its verdict, rationale, evidence, and the artifact revision examined. Such a verdict can satisfy a qualitative criterion. |

The scheduler can settle a goal when its required criteria have valid receipts for the current inputs. It can mark a goal blocked when a required dependency has no permitted way forward. Waiting for a running job, a scheduled retry, the next budget window, or a pending approval each has its own visible reason. Timers wake only work that is eligible. A model is called when the next operation needs judgment.

## PPTX pilot

A local six-page trial reached signed reviews and a verified merge in 12 min 57 s from the first source read. Six makers overlapped. Page 6 had passed independent review before page 5 produced its first candidate. An external harness started the page workflows and monitored their stop conditions. This establishes a normal-run concurrency baseline. Server recovery after losing both the client and the harness is the outstanding test.

For a reference-image deck, create an independent maker and reviewer assignment for every page. Each page carries its source digest, editable specification, rendered candidate, and accepted review revision. The maker receives the relevant reference, background if supplied, object list, and available edit operations together. Local tools can build and render the page while unrelated pages proceed.

Publish a page candidate as soon as its required checks pass. Its reviewer receives the reference and the render of that exact editable candidate, checks content and editability, and returns all material findings together. A score counts only for the artifact and rubric it identifies. Unknown source-font identity alone does not trigger a repair unless exact font identity is a stated requirement. A rendering or typography defect that changes readability still qualifies. A changed page invalidates its own verdict and any dependent assembly.

Stage accepted pages immediately. The final assembly joins their ordered digests and compiles once per accepted manifest. Verify any deck-wide properties introduced by compilation, such as slide order and missing assets. Reopen only the pages implicated by that verification. A delivery retry reuses the accepted deck. Retain sources, accepted pages, required evidence, and the final deck. Apply the configured retention policy to scratch renders and superseded full-size candidates.

## Rollout and acceptance

Start with one native OctosCode flow, `/goal fix the failing test`. Add the OUP wait and evidence projection behind a negotiated capability, then route test completion and approval responses through durable intake. Reuse existing goal and session IDs. Migrate an active goal at a safe turn boundary with one dispatcher owning its generation. Preserve existing budget and permission policies during rollout. Next, adopt the same activity contract for PPTX pages and their assembly join. Extend other inputs and delivery channels as they pass the same recovery tests.

| Acceptance test | Evidence required before enabling unattended mode |
|---|---|
| Close OctosCode after the server acknowledges the goal. Close it again while a test runs. | The server completes the authorized work. On reconnect the TUI shows the same goal, tested revision, and result. No model requests occur during the wait. |
| Kill the host after event persistence, after claiming work, and after result persistence but before successor dispatch. Duplicate the wake on restart. | Each acknowledged event is accounted for. Only the current lease can commit. The accepted test or review stays accepted and each logical successor is scheduled once. Exercise the normal wake path with periodic reconciliation disabled, and startup recovery separately. |
| Restart while waiting for approval. Send a late duplicate approval, then repeat with revoked authority. | A valid grant resumes the same operation once. A stale or revoked grant cannot execute it. |
| After two pages are signed and a third is still open, disconnect the client, terminate the external supervisor if present, and kill the host. Restart only `octos serve`. Redeliver a signed page's review event. | Both signoffs retain their original candidate and rubric digests. Those pages incur zero further model calls. The open page resumes, and one final artifact is published for the ordered manifest. Record provider calls by page and the final delivery key. |
| Install a new skill or rubric while a goal is parked. Resume once with the original snapshot and separately exercise an explicit upgrade. | Ordinary recovery uses the admitted versions. An upgrade records its scope. A delivery-only change preserves signoffs. A changed review criterion reopens only dependent reviews. |
| Fail final notification delivery after the artifact is accepted. | Reconnection shows the accepted artifact and outstanding delivery. Retry emits no generation, repair, or review calls. |

Measure from durable event acceptance to worker claim separately from provider latency, tool duration, review duration, and final assembly. Report median and p95 dispatch latency, peak page concurrency, critical-path elapsed time, duplicate model calls after acceptance, tokens spent while parked, and unresolved outcomes. Compare with the same source deck, model, rubric, and concurrency limits. The initial release gates are zero lost acknowledged events in the fault tests, zero idle model calls, and zero duplicate accepted effects for idempotent adapters. Any speedup claim needs an observed baseline and resulting timings.

This adds durable writes and requires adapters to define trustworthy evidence and replay behavior. Implementing it in the server makes those guarantees available to every client. The existing scheduler and workflow host provide an incremental path that also preserves interactive foreground use.

## Optional follow-up on standing instructions

Consider this capability when a user needs ongoing coverage, for example “watch this folder for a month, update changed slides, and notify me only when a decision is needed.” A standing instruction records the owner, permitted source and actions, expiry, revocation and notification conditions. It may create zero or more ordinary goals. Reuse Octos's existing scheduler, which already tests that a one-shot timer survives until delivery is acknowledged. Anthropic's guidance on batching events and choosing when to notify applies at this boundary. Changes to the instruction are ordered per instruction, while work on independent pages stays concurrent. [Octos timer delivery](https://github.com/octos-org/octos/blob/6cde67b0c380b80e2028f8390573a1a636b220b3/crates/octos-bus/src/cron_service.rs#L1639-L1670) · [Anthropic, Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)

Before enabling a folder watch, test three rapid saves followed by a duplicate event for the same final revision. It should produce one update for that revision and respect the notification rule. After cancellation or expiry, a delayed event must start zero goals. Count model calls during quiet periods and require zero. The one-goal recovery milestone can ship independently.
