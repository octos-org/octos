# Durable finite-goal recovery in Octos

**Status** Proposed · **Date** 2026-11-21  
**First client** OctosCode · **First workflow integration** editable PPTX production

## Decision

Give `octos serve` ownership of an unattended goal from admission through delivery. Once the server acknowledges an unattended goal, it must be able to answer three questions after a restart. What work has been accepted? What can run next? If nothing can run, which event or decision will unblock it? OctosCode can disconnect and later obtain those answers through the Octos UI Protocol (OUP). A waiting goal consumes zero model tokens.

For each opted-in goal generation, the Rust `octos-fleet` kernel is the sole authority for attempts, accepted results, and successor dispatch. Its redb store already supports fenced completion, budget settlement, boot reconciliation, and an outbox with claim and acknowledgement. Extend its transactions for the intake and successor records below. OctoScript declares dependencies and joins. Rust and Relax activities validate domain evidence. Agents plan, edit, and review. The supervisor ledger continues to serve legacy goals and session history. A PPTX receipt journal supplies immutable evidence to fleet. Neither journal can authorize a second attempt for a fleet-owned generation. [Fleet kernel spec](../FLEET-KERNEL-V1-SPEC.md) · [Completion transaction](../../crates/octos-fleet/src/store.rs#L1157) · [Boot reconciliation](../../crates/octos-fleet/src/store.rs#L2191) · [Outbox](../../crates/octos-fleet/src/store.rs#L2547)

Fleet v1 dispatch requires the keeper profile and a bound fleet plan. Offer the pilot only after both conditions hold. A client using another profile keeps its existing execution mode. [Fleet admission checks](../../crates/octos-cli/src/autonomy/agent_orchestrator/mod.rs#L8442-L8480)

## Why change the current behavior?

- **OctosCode can show an active goal while no turn is eligible.** The Rust client submits the objective to the server. The ordinary continuation policy checks token and turn budgets, a minimum interval, and an hourly cap. In the examined release it derives the turn cap as `ceil(token_budget / 2500)`. The goal indicator mainly shows status and token consumption. Someone with tokens left cannot tell from that indicator when work will resume. [Client submission](https://github.com/octos-org/octoscode/blob/3b4efa77682cf130a195f6bc6c9a894ab9fd0200/src/store.rs#L2367-L2394) · [Continuation policy](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/autonomy/agent_orchestrator.rs#L15681-L15732) · [Goal indicator](https://github.com/octos-org/octoscode/blob/3b4efa77682cf130a195f6bc6c9a894ab9fd0200/src/app.rs#L3687-L3705)
- **The runtime can confuse activity with progress.** The turn-end check treats a positive token count as progress even if the model reread the same file and produced the same diagnosis. Three consecutive zero-token failures can park a goal. Separately, the completion verifier historically rejected finished peer work when its evidence was missing from the request. The existing fix passes ledger findings to that verifier. [Turn-end check](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/autonomy/agent_orchestrator.rs#L3629-L3666) · [Failure threshold](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/autonomy/agent_orchestrator/contract.rs#L84-L91) · [Verifier evidence fix](https://github.com/octos-org/octos/blob/v2.1.0-rc.1/crates/octos-cli/src/goal_tool.rs#L1177-L1207)
- **The PPTX work supplies a reusable precedent.** The experimental workflow branch binds each activity to an operation, generation, and validated receipt. A worker can exit before its receipt arrives. Replaying the exit chooses the same successor. The local prototype implements this in `1283ecae0` and tests recovery with periodic draining disabled in `9d3bd3128`. Both commits are unpublished. The upstream integration points are the [continuation scheduler](https://github.com/octos-org/octos/blob/6cde67b0c380b80e2028f8390573a1a636b220b3/crates/octos-cli/src/autonomy/master_continuation_scheduler.rs) and [supervisor store](https://github.com/octos-org/octos/blob/6cde67b0c380b80e2028f8390573a1a636b220b3/crates/octos-cli/src/autonomy/supervisor_store.rs). The [rollout and acceptance tests](#rollout-and-acceptance) specify how to verify the proposed recovery guarantee upstream.

## Execution and recovery contract

Ordinary `GoalContinue` requests already use `enqueue_and_persist_continuation`. On boot, the orchestrator reads unfinished `PendingContinuationRecord` entries from the supervisor store, rebuilds the requests, and restores their attempt numbers in the in-memory scheduler. Its short recent-claim guard applies to external wakes. Recurring goal continuations have no such guard. The new guarantee is that a migrated goal can recover the outcome of an individual operation and dispatch its successor once. [Goal enqueue](../../crates/octos-cli/src/autonomy/agent_orchestrator/mod.rs#L13493-L13503) · [Startup replay](../../crates/octos-cli/src/autonomy/agent_orchestrator/mod.rs#L1393-L1423) · [Guard by wake type](../../crates/octos-cli/src/autonomy/master_continuation_scheduler.rs#L553-L564)

1. **Accept an event before acknowledging it.** Durably record its source, stable occurrence ID, goal, operation, generation, and payload reference. Tool results, worker returns, reviews, approvals, and due timers follow the same rule. Redelivery carries the same occurrence ID across restarts.
2. **Give each independent operation one current owner.** Fleet claims a ready operation, records the attempt and lease, and reserves its budget in one transaction. Completion must match the current attempt, lease, and input generation. Independent pages may run concurrently within resource limits. [Fleet claim](../../crates/octos-fleet/src/store.rs#L889)
3. **Commit the result and successor together.** In one fleet transaction, consume the occurrence, accept the validated receipt, settle the attempt's budget, and record its successor, wait, or terminal state. Redelivery finds the recorded disposition. The dispatcher derives work from ready records, due timers, recoverable attempts, and pending outbox effects. Any external effect uses a stable operation key. In-memory wakes reduce latency.
4. **Persist a wait before releasing the worker.** For a deferred approval, persist the request and operation IDs, argument digest, authorized owner, profile, workspace, scope, generation, and expiry. Today the pending and consumed sets are in memory. On response, revalidate the grant and current permissions. Atomically record consumption and make that exact operation eligible before releasing it to execute. Duplicate, expired, revoked, or superseded grants cannot release it again. Resolve credentials at execution time. When a wait needs its owner, commit the wait and notification intent together under `(goal, generation, wait_id)`. Use the existing routing and notification preferences. A reconnect exposes the unanswered request even if no external channel is configured. [Pending approvals](../../crates/octos-agent/src/approval.rs#L268) · [Human events](../../crates/octos-cli/src/autonomy/human_events.rs#L168) · [Escalation routing](../../crates/octos-cli/src/autonomy/escalation_notify.rs#L64)
5. **Make delivery independently recoverable.** Commit a pending notification with the terminal result, its destination, and a delivery key. A dispatcher handles retries. A failed attachment upload leaves the completed artifact intact. If an external destination can neither deduplicate nor confirm a prior send, expose delivery as *unconfirmed* and reconcile before repeating an irreversible action. This design assumes at-least-once event delivery. It requires idempotency or a queryable result at each effect boundary.

**Ordinary agent turns recover one tool operation at a time.** Persist the intent, exact arguments or their immutable reference, and input tree digest before execution. Commit the result with its evidence. An intent without a confirmed result has outcome `unknown`. A new model turn starts from the last committed evidence and the state of outstanding operations. A test declared safe to repeat can run against the same tree. A push, deploy, or send with an unknown outcome needs an idempotency guarantee or a destination check before retry. If neither establishes a safe next action, expose the uncertainty and park the operation. A store lease fences result acceptance. Before a successor writes, stop and reap any surviving subprocess, or isolate it from the successor's workspace and publication path. [Fleet spec on surviving processes](../FLEET-KERNEL-V1-SPEC.md#recovery-reconciliation-boot)

**Working tree.** Each coding goal generation owns one isolated worktree and immutable base commit. Persist the binding. On reconnect, the interactive client may inspect that goal while the user edits a separate checkout. Only the current owner may write the goal tree or publish its patch. Reclaim it only after fencing the prior writer. Compare the current target base before integrating work. [Existing peer worktree policy](../../crates/octos-cli/src/peers/mod.rs#L2863-L2878)

**Service lifetime and visibility.** Advertise unattended mode only for an independently supervised `octos serve`, such as a launchd or systemd service. A private stdio backend can advertise foreground execution. While the server is down, show the last acknowledged state with the server marked unreachable. At boot or after sleep, reconcile overdue timers and lease ownership before dispatch, including any surviving worker. On reconnect the OUP projection shows the goal phase, last accepted evidence, pending operation, wait reason, next eligible time, remaining budget, and delivery status. [launchd service](../../scripts/install.sh#L687) · [systemd service](../../scripts/install.sh#L750-L752) · [OctosCode transport and lifetime](https://github.com/octos-org/octoscode/blob/3b4efa77682cf130a195f6bc6c9a894ab9fd0200/README.md#L202-L225)

### Workflow versions during recovery

At admission, pin the OctoScript workflow, skills, review rubric, and loadable executors (including Relax/JIT activities) by immutable reference. Retain them while the goal is recoverable. Record the serving host build as provenance and the versions of the record format and activity interface. An upgraded host can resume once it can read the records and honor the pinned activity interface. If it cannot, report the incompatible version before claiming work. Report a missing pinned artifact separately. Each review records its candidate, rubric, and executor digests, so a change to a JIT QA implementation is visible. [LoopForge workflow lookup](https://github.com/Tencent/LoopForge/blob/a458320ec989c9dbc08a3c4987a63498ff2c87d2/internal/engine/workflow_graph.go#L41-L50)

On an explicit upgrade, record the old and new versions and which acceptance criteria or inputs changed. A change to notification retries preserves page signoffs. A new editability criterion reopens the affected reviews against the existing candidates. A maker runs again only if a finding requires changes to its artifact.

## Progress, completion, and diminishing returns

At admission, bind each criterion to its source (user instruction, policy, or accepted workflow), owner, verifier, and evidence requirement. A worker may propose criteria. Only the named owner can authorize a waiver, recorded with its scope and reason. The designated reviewer opens a finding against a specific artifact and object. The runtime assigns a persistent finding ID that carries across repair attempts. Keep large artifacts by immutable reference and digest. On recovery load the current operation, relevant evidence, and applicable user instructions. Token counts remain useful for cost accounting.

| Observation | Runtime decision |
|---|---|
| A coding task produces a patch and a failing test now passes | Attach the test command, exit status, and tested tree digest. Advance criteria satisfied by this evidence. Other criteria stay open. |
| A provider times out before returning a result | Release the worker. Reconcile any unknown external effect before scheduling a safe retry with bounded backoff. Surface the reason, retry time, and exhausted retry budget. |
| An agent repeats a repair against the same input and the same material findings remain | Compare persistent finding IDs and fresh evidence. Batch independent fixes into one attempt. After the operation's bounded retry policy is exhausted, record unresolved findings and the best reviewed candidate. A required criterion stays unresolved until met or explicitly waived by its owner. |
| An operation requires judgment or has no mechanical acceptance test | A designated reviewer records its verdict, rationale, evidence, and the artifact revision examined. Such a verdict can satisfy a qualitative criterion. |

Fleet can settle an opted-in goal when its required criteria have valid receipts for the current inputs. It can mark a goal blocked when a required dependency has no permitted way forward. Waiting for a running job, a scheduled retry, the next budget window, or a pending approval each has its own visible reason. Timers wake only work that is eligible. A model is called when the next operation needs judgment.

## Coding goal pilot

For `/goal fix the failing test`, admit one named test that fails on a recorded immutable base revision. Bind its command, evidence requirement, budget, isolated worktree, and restricted tool scope before editing. The pilot may read, patch, and run the authorized test locally. Its verifier runs the admitted test independently on the resulting tree and records the tree digest, command, exit status, and output digest. Deliver the patch and its test receipt. This first slice can run with preauthorized tools. A workflow that requires a deferred grant must also pass the approval gate below.

## PPTX pilot

In a local six-page, harness-assisted run, all six Octos makers overlapped. Page 6 passed review before page 5 produced its first candidate. OctoScript sequenced each page, but the Rust benchmark host invoked a Python adapter for every page activity. Python launched the workflows, validated verdicts and signoffs, and drove assembly. `codex exec` generated the artwork plates, Paddle performed OCR, and the PPTX runtime was a staged JIT copy. The recorded **776.62 s** ran from the first art `reader_started` event to the verified merge (**908.59 s** from host start). These timings describe that harness. A Rust, Relax, and OctoScript server still needs its own baseline and recovery test.

For the native pilot, Rust owns dispatch and receipt validation, OctoScript declares parallel page activities and their final join, and Rust or Relax activities perform authorized OCR, rendering, and assembly. The pilot can use supplied artwork pinned by digest. The user has not decided whether Octos may call an image provider or the Codex CLI for generated artwork.

For a reference-image deck, create an independent maker and reviewer assignment for every page. Each page carries its source digest, editable specification, rendered candidate, and accepted review revision. The maker receives the relevant reference, background if supplied, object list, and available edit operations together. Local tools can build and render the page while unrelated pages proceed.

Publish a page candidate as soon as its required checks pass. Its reviewer receives the reference and the render of that exact editable candidate, checks content and editability, and returns all material findings together. A score counts only for the artifact and rubric it identifies. Unknown source-font identity alone does not trigger a repair unless exact font identity is a stated requirement. A rendering or typography defect that changes readability still qualifies. A changed page invalidates its own verdict and any dependent assembly.

Stage accepted pages immediately. The final assembly joins their ordered digests and compiles once per accepted manifest. Verify any deck-wide properties introduced by compilation, such as slide order and missing assets. Reopen only the pages implicated by that verification. A delivery retry reuses the accepted deck. Retain sources, accepted pages, required evidence, and the final deck. Apply the configured retention policy to scratch renders and superseded full-size candidates.

## Rollout and acceptance

Start with the coding pilot behind a negotiated OUP capability, then adopt the same contract for PPTX. Preserve existing goal and session IDs, budgets, and permissions. To migrate, stop admitting legacy work for the goal, drain or fence its outstanding attempt and durably hand ownership to fleet at a safe boundary. Both dispatchers must consult that per-generation ownership decision before issuing work, including after restart. Rollback uses the same handoff in reverse after the fleet attempt is settled or reconciled. Already accepted effects retain their occurrence IDs and receipts across either handoff.

Run the shared gates and the rows for the pilot being enabled. The deferred-approval row gates permission to suspend and resume a tool for approval.

| Gate | Acceptance test | Required evidence |
|---|---|---|
| Shared | Kill the host after event persistence, after claim, and after result commit before dispatch. Redeliver the same wake. | Each acknowledged event is accounted for, only the current attempt commits, and each logical successor runs once. Exercise normal event delivery with periodic reconciliation disabled and boot recovery separately. |
| Shared | Kill the service and let launchd or systemd restart it with clients disconnected. Separately suspend the machine across a timer deadline and a lease expiry. | The client reports the outage. On reconnect it sees the same goal. Each overdue occurrence runs once and no surviving worker can race a replacement. Waiting incurs zero model calls. |
| Shared | Park on an owner-required wait, disconnect, and retry notification delivery. | The wait and its notification share one durable key. The owner can find the outstanding decision on reconnect. A retry uses the same key and follows the configured notification policy. |
| Shared (deferred approvals) | Restart while waiting for approval. Deliver a valid response twice, then repeat with revoked authority or a newer goal generation. | A valid grant releases the recorded call once after consumption is durable. An invalid grant releases no call. |
| Shared | Cancel or supersede a running tool, then deliver its late result. Exhaust the budget separately after an attempt reserves it. | Stale work cannot publish or schedule successors. Reconcile any outstanding effect. Settle the reservation once against actual usage or release the unused reservation. No further charged attempt starts without budget. |
| Shared | At migration send the same occurrence to both dispatchers. Request rollback with a fleet attempt still outstanding. | Only the recorded owner issues work. Rollback waits for reconciliation or completion before restoring legacy ownership. One accepted effect, successor, and budget settlement survive redelivery. |
| Shared | Upgrade the serving host while a goal is parked. Separately install a new skill or rubric and exercise an explicit upgrade. | A compatible host resumes with pinned dependencies. An incompatible reader or activity interface gives a visible reason before claim. Changing delivery preserves signoffs. Changing a criterion reopens only dependent reviews. |
| Shared | Fail final notification delivery after accepting the result. | Reconnect shows the artifact and outstanding delivery. Retry makes zero generation, repair, or review calls. |
| Coding goal | Close OctosCode after admission and again while the named test runs. Kill the host after the patch is written, before verification. | Recover the patch in the bound worktree. Verify the actual tree and return the patch and receipt to the reconnected client. A committed edit is applied once. |
| Coding goal | Kill the host after the test passes, before acknowledgement. Exercise a committed receipt and a lost result separately. | Reuse a committed receipt without rerunning the test. An unknown result permits a rerun only of the repeatable test on the same tree digest. Deliver once. |
| Coding goal | Edit the interactive checkout concurrently. Leave an obsolete subprocess alive and attempt to write or publish after reclamation. | The user's independent edits survive. Stop or isolate the old writer before the successor writes. Only the current attempt can publish a patch for the verified tree. |
| PPTX | Run with only supervised `octos serve`. Disconnect after two pages are signed and a third is open. Kill the host, let the service restart, and redeliver one signed page's review. | Both signoffs keep their candidate and rubric digests. Those pages incur zero further model calls, the open page resumes, and the ordered manifest produces one delivery. Record calls by page and the delivery key. |

Measure from durable event acceptance to worker claim separately from provider latency, tool duration, review duration, and final assembly. Report median and p95 dispatch latency, peak page concurrency, critical-path elapsed time, duplicate model calls after acceptance, tokens spent while parked, and unresolved outcomes. Compare with the same source deck, model, rubric, and concurrency limits. The initial release gates are zero lost acknowledged events in the fault tests, zero idle model calls, and zero duplicate accepted effects for idempotent adapters. Any speedup claim needs an observed baseline and resulting timings.
