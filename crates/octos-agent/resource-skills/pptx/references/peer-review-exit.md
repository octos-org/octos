# Peer 评审与退出

用于 PPTX 成品制作与返修。用户明确指定 solo、独立模型对照或仅查阅时，保留该范围，不暗加评审反馈。这里的模式是独立评审会话与持续制作 peer 协作；不是每页启动一个 worker，也不是把一次额外视觉 API 调用称为 peer。

## 开始时落实角色与运行状态

角色按职责分开，不能把同一制作会话的几段自述称为独立验收。需要高层仲裁时，主会话作为 supervisor，只保留任务、当前稿、缺陷状态和退出条件；制作 peer 是唯一源稿 writer，独立 reviewer peer 直接读取原图、底图和实际 PPTX 渲染。QC 的可测部分由 Rust 执行：校验文件绑定、文字覆盖、几何约束、评审覆盖和旧证据失效。Rust 不替代视觉判断，也不能证明 reviewer 理解了图片。通常是三个 LLM 会话加确定性工具，而不是四个会话重复全量看图；用户已指定独立 QC 模型时再单独配置。

reviewer 首轮先看原始证据，再读制作者的解释，避免被“有意设计”先入为主。fixer 可以用当前图提出反证，但不能直接关闭 reviewer 的必修项。supervisor 只仲裁具体冲突及停滞，不代改坐标、不复制制作者的通过声明。两个会话的旧运行仍需如实写为“协调兼评审 + 制作”，不能追认成三会话或四会话。

首稿前的 reviewer 只需记录视觉关系和高风险区域，不提前写逐对象长报告。正式检查把观察直接写进 Rust 评审模板，并在交接中只列必修项、争议和未覆盖范围；避免再手抄一份相同报告。复核采用变化区域及邻居，未改变且绑定仍有效的证据复用。工具无法验证的项目保留 unknown；视觉评审通过但必要 gate 未过时，统一标记“视觉已评审、验证未完成”，不能一份记录称完成、另一份称阻塞。

持续终端恢复时应重连同一 staged peer，而不是重发 `peer_handoff` 创建同名新任务。支持恢复的版本会核对原 owner、workspace 和关闭状态，并保留同一历史与预算。旧 peer 缺少持久化 workspace 绑定时应报恢复限制，不能猜目录；宿主不再存在也不能把旧状态称为仍在工作。该恢复能力只在对应构建验证后可宣称启用。

- **协调主会话**：保持简洁的目标、缺陷和验收上下文，只写协调记录，仲裁具体冲突与退出；不代改页稿、坐标或生图 prompt。
- **独立评审 peer**：只读稿件，直接看原图、底图和当前实际渲染；只写评审产物，按稳定缺陷 ID 复核，不直接改制作源稿。
- **制作 peer**：独占源稿及交付物写入，复用已安装的 skill、builder、字体和 renderer，决定具体修法并自查。模型沿用用户选择。旧 writer 实际停止后才交接；已有有效内容、底图和检查不重做。
- **真实机制**：Octos 用 `peer_handoff`，按部署版本的 schema 调用 `peer_list` / `peer_gather` / `peer_send_input`；保存真实 peer 和会话标识。其他宿主使用有独立上下文和持续生命周期的等价会话能力；能力缺失时说明缺口，不悄悄降级为自己制作自己验收。
- **看图能力**：制作与评审会话都必须收到实际图片内容；协调者裁决视觉争议时也必须看对应原始证据。路径、OCR、制作方的文字结论不能替代直接看图。一次验证已知 PNG 传入即可，不每轮重做环境测试。
- **退出能力**：Octos 按 [证据接入](continuation-evidence.md) 绑定整稿制作 peer 的真实 session，记录 policy 检查结果；首个完整检查周期后核验 runtime 已消费该证据。缺少接线不允许被描述成“有阈值保护”。若宿主不支持内核观察器，明确只有协调者执行退出约定，没有硬性内核保障。

在已有制作记录里写下上述事实和用户已有的时间/费用预算，不另建项目专用 harness。初始化策略前确认任务/owner；Octos 的 `pptx_tool.evidence_init` 由宿主注入 owner，省略手填昵称。`evidence_status.owner_matches` 必须为真，完整周期后还要核验 `runtime_consumed_current_evidence`；配置文件存在不代表接通。同目录只设一个整稿策略 owner，评审者不要覆盖制作 peer 的策略。多个独立制作任务必须使用各自策略作用域。

## 冻结验收范围，避免越修越多

第一次整稿评审时，将问题分成：

| 类别 | 判断依据 | 处理 |
|---|---|---|
| 必修 | 违背用户要求；错漏文字或数据；不可编辑/文件损坏；实际阅读尺寸下遮挡、截断、错误归属、错误图文关系；未核实的产品外形修补 | 保留为 open/unknown，修好并用当前实际渲染复核 |
| 可选微调 | 不影响正确性、阅读或明确设计约定的细小留白/边距差异、个人风格偏好 | 写入 backlog；不单独发起新的返修轮次 |

严重性依据影响判断，不按页号或固定像素阈值判定。不能为了退出把真实错位降成可选，也不能在检查通过后临时追加审美偏好。新发现的必修缺陷与回归仍须处理，记录发现原因；新可选项不重置原缺陷的停滞历史。缺少必要检查是 unknown，不是 pass。

先读 Rust 返回的 `native_qa.diagnosis`（review_pack 位于 `finding_summary.diagnosis`）：实测违反约束、待视觉裁决的接触/可见性问题、以及缺少证据或工具无法测量的情况是三种不同任务。不能把所有 unknown 当成要移动文字的缺陷，也不能把所有接触都说成装饰。遇到不支持的边界测量，应报告能力缺口，不能循环改稿凑零。未知数因报告分类而下降，并不证明同一个视觉缺陷已有实质改善；诊断字段只是反馈，不是新增的内核退出保障。

约定“必要检查”时写明验证路径：工具可测量的约束、独立视觉判断、当前工具不支持的检查分别记录。不能把不支持的测量暗改成通过，也不能把机器未知总数清零当作排版目标。模型对照实验使用相同的内容拆分权限、设计调整范围和验收路径；不能一方靠视觉验收，另一方被要求所有机器告警清零。若已冻结的宿主契约仍要求不支持项通过，报告契约与能力不匹配并交回，不修改画面或重置历史来迎合计数；本说明本身不会改变内核 gate。新任务可按 [review lifecycle](review-lifecycle.md) 在初始化时冻结独立视觉验证路径；旧任务保持原契约。

对必修项保留稳定 ID、影响、当前证据、最近修法、通过条件与连续无改善次数。无需给每个文本框建台账；同一原因可以分组，但不能用改名称、换 peer 或另起任务清掉历史。内核现有四类聚合计数不能代替协调者对同一缺陷的判断。

## 每轮修复与复核

首次可读整稿/选定范围的 `cycle` 就交回 `peer_review_handoff`，包括确切源稿、实际渲染和当前未知项；不要先自修到“满意”才首次交回。首发前 Maker 只核对构建/文件/页数；完整逐对象 review_pack/验收模板由 Reviewer 独占。Maker 修复时看所需局部，修后复查改动与邻居，不与 Reviewer 重复完整逐对象审查。`notification_sent:false` 表示构建工具未通知；Octos 制作者用 `peer_publish` 发布确切产物路径，协调者 `peer_gather` 读取后用 `peer_send_input` 派发。制作/评审 peer 没有主会话专用的 `peer_send_input`，不要用 subagent 的 `send_input` 代替。评审主会话可直接查看共享工作区的首稿，不必等待最终交付。后续按原因批量修复，不要求每个候选都另起一个 peer。此约定不是内核强制的首轮通知。

1. 制作者批量处理一组同原因缺陷，复用公共工具；不要每挪一个字就重跑整稿。每个已完成的“改稿—渲染—检查”周期都记录证据，不能只把最后交回评审者的次数当作总修复次数。相同输入的轮询或重复记录不计新周期。
2. 交回确切 PPTX、对应实际渲染、改动范围和未解决项。评审者先看全页，再看有上下文的局部图；复用未改页面的有效证据，最终整稿再扫一遍。
3. 评审者独立检验通过条件。检查一个图形的完整边界、基线和所有重复元素；不能只统计一侧刻度、仅核对文字内容或只看模型圈出的区域。工具误报需说明证据，不篡改阈值换取通过。
4. 发现必修缺陷立即用 `finding_register` 保存当前局部证据，再发布给协调者；最终 `review_submit` 保留该登记回执。协调者把反馈发给同一个制作 peer，包含实际观察、影响及验收条件，不交付未经验证的坐标或代码。重开一个 peer 不等于提出了新的修法。
   - 涉及“原稿没有边框”“标签在图形外”等原稿对比判断，必须同时查看原稿与当前稿的对应局部；不能把 OCR 框、裁图截断或记忆当作图形边界。制作方发现反馈与图片冲突时，提供原图证据并说明，不盲目照改。
   - 可选间距或非精确字体复制的细微差异不能作为继续返修的唯一理由。涉及工具能力限制时先查实际 schema/字体信息，区分不能表达的功能与可修复的错位；保留限制说明。
5. 等待已命名的制作 peer 时，使用 `peer_gather` 的 `wait_ms`（单次最多 60000 ms），所选 blackboard 变化时提前返回（不保证每种状态变化都有新内容）；超时不代表完成，旧结果不代表本轮结果。还有独立工作就继续做。仅在已确认宿主持续运行并处理完成通知时，才可结束当前轮等待唤醒。`octos chat --message`/位置参数属于单次宿主，主回合结束可能关闭进程内 peer；不要将它作为持续协作宿主或承诺回合结束后仍会继续。使用保持打开的交互式会话或已验证的常驻服务。不要用长串 shell `sleep` 占住评审主会话。其他宿主使用其实际支持的完成通知。
6. 外部作业 pending 时保留真实 job ID，等完成事件或有界查询；等待本身不算修复失败，不重复提交，不靠不断催促制造进度。

## 退出标准

| 状态 | 条件 | 行动 |
|---|---|---|
| 完成 | 必修项全部关闭，必要检查无 unknown，最终文件与受检稿一致，实际整稿复核通过 | 交付；可选微调列出即可，不为它们重开一轮 |
| 需要重规划 | 同一必修问题连续 3 个完整检查周期没有实质改善，或反复在几种错误间来回 | 停止原修法，保留产物与证据，诊断不同原因；没有可执行的新假设就交回未完成结果 |
| 诊断后仍停滞 | 一次不同原因的诊断/修复检查仍未改善，或收到宿主的 `needs_replan` yield | 制作 peer 交回；协调者不能只发“继续”，不能换名字重启以绕过退出 |
| 真实阻塞 | 必需素材、权限、配额或工具故障，且当前没有可行的已授权替代路径 | 报告具体依赖、错误与已有成果；不把阻塞称完成 |
| 预算达到 | 用户/宿主给定的时间、费用或运行预算用尽 | 停止派新任务，按宿主取消/收尾机制交回当前稿和未完成项，不擅自续费或扩大预算 |

“实质改善”须是该缺陷在同一通过条件下可观察地减轻或消失，且没有同等/更严重回归。工具调用增加、输出新文件、改检查框、关闭另一个可选项，不算该缺陷的改善。一个全新诊断可以改变方法，不能改验收标准或抹去累计记录。

3 是默认停滞诊断窗口，不是最多三轮，也不是任意时间内必然结束的保证；用户的明确窗口优先。未给总预算时不能捏造一个，但必须执行上述验收退出与停滞交回。技能约定由模型执行；内核只能强制其实际支持且已接通的部分，不能宣称技能文字本身构成硬性截止。

退出时简要报告：状态、当前 PPTX/预览、已关闭与未解决的必修项、实际检查范围、总修复周期/评审轮数，以及可得的耗时/费用。停止执行不等于通过验收。
