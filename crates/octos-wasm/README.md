# octos-wasm

Browser/JS client-side binding of octos's protocol + utility types
(`octos-core`). Use it to (de)serialize the `octos serve` WS/REST protocol and
model messages/tasks/IDs in a web frontend. The AGENT LOOP does NOT run
in-browser — `redb` (filesystem), `tokio` threads, native TLS, and llama.cpp
cannot target `wasm32-unknown-unknown`; run the agent via `octos serve`
(native) and talk to it over the network. For native embedding use `octos-ffi`
(C-ABI), `octos-uniffi` (Python/Swift/Kotlin), or `octos-pyo3` (Python wheel).

## Why only `octos-core`?

`octos-core` is the leaf crate — shared protocol types + codecs with pure deps
(`serde`, `serde_json`, `chrono`, `uuid`, `eyre`, `tracing`, `sha2`). It is the
only octos crate that can compile to `wasm32-unknown-unknown`. The heavier
crates are hard blockers in the browser:

| Blocker | Where | Why it can't target wasm |
| --- | --- | --- |
| `redb` | octos-memory, octos-agent | memory-mapped file database (filesystem) |
| `tokio` `rt-multi-thread` | octos-agent | no OS threads in the browser |
| `reqwest` + `rustls` + `blocking` | providers/channels | native-only HTTP/TLS |
| llama.cpp embedder | octos-embed-llama | C++/emscripten, not `wasm32-unknown-unknown` |

So this crate is the **protocol + utility layer** only. Run the agent
server-side; do the wire (de)serialization and ID/message modelling in the
browser with this binding.

## wasm feature-gating

A naive `cargo build --target wasm32-unknown-unknown -p octos-core` **fails**:

```
error: specify a source of randomness using one of the `js`, `rng-getrandom`,
       or `rng-rand` features
```

because on `wasm32-unknown-unknown` `uuid` gates `getrandom` off and needs a
browser randomness/time source. This crate fixes it by declaring, **only for
the wasm target**, the feature-carrying deps that Cargo unifies onto the same
`uuid`/`chrono` packages `octos-core` already uses (see `Cargo.toml`):

```toml
[target.'cfg(target_arch = "wasm32")'.dependencies]
uuid  = { version = "1",   features = ["js"] }       # WebCrypto RNG + Date.now() for UUID v7
chrono = { version = "0.4", features = ["wasmbind"] } # Utc::now() via JS Date
```

`js` alone is sufficient on `wasm32-unknown-unknown` (uuid uses `wasm-bindgen`
directly for both randomness and the clock — no extra `getrandom/js` needed).
On the host target these lines are absent, so the native
(`getrandom`/`SystemTime`) paths are used unchanged.

## Build

```bash
cargo install wasm-pack          # if not already present
wasm-pack build --target web     # emits pkg/ (.wasm + JS glue + .d.ts)
```

`pkg/` and `*.wasm` are build artifacts and are git-ignored — do not commit
them.

## Test

```bash
wasm-pack test --node            # wasm-bindgen-test suite (tests/web.rs)
cargo test -p octos-wasm         # pure-logic layer on the host target
```

## JS/TS usage

```js
import init, {
  decode_ui_frame,
  encode_rpc_request,
  truncate_utf8,
  new_turn_id,
  new_client_message_id,
  new_thread_id_rooted_at,
  message_user,
  session_key_new,
} from "./pkg/octos_wasm.js";

await init(); // loads the .wasm; installs the panic hook (start())

// 1. Model a session + a user turn, client-side.
const key = session_key_new("web", "demo");            // "web:demo"
const cmid = new_client_message_id();                  // UUID v7 (optimistic-UI token)
const threadId = new_thread_id_rooted_at(cmid);        // == cmid
const turnId = new_turn_id();                          // UUID v7 for this turn
const msg = message_user("summarize this repo");       // plain JS object

// 2. Encode a client -> server `turn/start` request frame for the WebSocket.
//    Shape mirrors octos-core's `TurnStartParams`: session_id + turn_id +
//    input items (each `{ kind: "text", text }`).
const frame = encode_rpc_request("req-1", "turn/start", {
  session_id: key,
  turn_id: turnId,
  input: [{ kind: "text", text: msg.content }],
});
socket.send(frame);

// 3. Decode a server -> client frame off the wire.
socket.onmessage = (ev) => {
  try {
    const { kind, frame } = decode_ui_frame(ev.data);
    // kind: "request" | "response" | "error" | "notification"
    console.log(kind, frame);
  } catch (rpcErr) {
    // rpcErr is a JSON-RPC error object: { code, message, data? }
    console.error("bad frame", rpcErr.code, rpcErr.message);
  }
};

// Utilities.
truncate_utf8("a very long string…", 8, "…"); // UTF-8 safe clamp
```

TypeScript declarations (`pkg/octos_wasm.d.ts`) are generated by `wasm-pack`.

## Exposed surface

- Init: `start()` (auto-runs on load; installs `console_error_panic_hook`).
- Utilities: `truncate_utf8` (`max_bytes` is a JS number; throws
  `invalid_params` on a non-integer / out-of-range value), `safe_filename`,
  `tool_output_limit`.
- IDs: `new_task_id`, `new_turn_id`, `new_client_message_id`,
  `new_thread_id_rooted_at` (rejects an empty id).
- Messages: `message_user`, `message_assistant`, `message_system`,
  `message_user_with_cmid` (return plain JS objects).
- Session keys: `session_key_new`, `session_key_with_topic`,
  `session_key_base`, `session_key_topic`, `session_key_profile_id`.
- Protocol constants: `ui_protocol_version`, `jsonrpc_version`,
  `max_text_frame_bytes`.
- Wire codec (decode, server->client): `decode_ui_frame`,
  `decode_ui_ndjson_frame` — return `{ kind, frame }`. Integer fields beyond
  JS's safe range (`> 2^53`, e.g. `u64` cursor/sequence numbers) decode as
  `BigInt` (lossless).
- Wire codec (encode, client->server): `encode_rpc_request`,
  `encode_rpc_notification`, `encode_rpc_request_ndjson` — return a compact
  JSON string frame. `params` must be strict, finite JSON: `undefined`, `NaN`,
  `Infinity`, and `BigInt` are rejected with a structured `invalid_params`
  error (never silently coerced to `null`), and a frame larger than
  `max_text_frame_bytes()` is rejected with `frame_too_large`.

All fallible exports reject with a JSON-RPC error object (`{ code, message,
data? }`) — the same shape `decode_ui_frame` rejects with — never a bare
string.
